# Conformance fixtures

Shared test data for rules that **two implementations have to agree on**.

Go Forth!'s server is Python (JQ-303) and its client is TypeScript. Some
calculations have to exist on both sides — not because anyone wanted them twice,
but because the alternative is a network round trip on every tap of the plan
screen. Where that happens, the server is authoritative and the client runs a
copy, and these files are what stop the copy drifting.

Each fixture is **generated from the Python implementation** and checked in.
Both test suites read it:

| file | generated by | Python check | TypeScript check |
|---|---|---|---|
| `spell-resolver.json` | `python -m app.scripts.export_conformance` | `api/tests/sim/test_conformance.py` | `client/src/plan/spellResolver.test.ts` |

To regenerate after a deliberate rules change:

```bash
cd api && python -m app.scripts.export_conformance
```

Then run both suites. A change that was not deliberate shows up as a Python
failure (the checked-in file no longer matches the resolver) *and* a TypeScript
one (the client no longer reproduces the file), which is the point — neither
side can be made green by editing the fixture alone.

## What is pinned, and what is not

Numbers, eligibility answers, reason strings, contributors, and the ids the sim
holds each side's resolved spells under. **Not** the prose on a card or the
summary sentence a server builds for display: those differ by language and by
wording, and pinning them would turn a copy edit into a cross-language build
failure.

Floats are compared **by parsed value, not by bytes**. Python writes `35.0`
where JavaScript writes `35`, and `1e-06` where JavaScript writes `0.000001`.
Byte-identical determinism is a claim about one implementation reproducing its
own output; agreement between two languages is a different claim, and conflating
them sends you chasing an impossible one (`api/CONVENTIONS.md`).
